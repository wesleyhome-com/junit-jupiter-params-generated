JUnit Jupiter Parameterized Test Extension

This project extends JUnit Jupiter parameterized tests with generated parameter values for numbers, date/time types, strings, booleans, and enums.

It is designed to reduce @MethodSource boilerplate while preserving type safety and adding compile-time validation for supported annotations.

Core Sources

  • Numeric ranges: @IntRangeSource, @LongRangeSource, @DoubleRangeSource, @FloatRangeSource

  • Numeric explicit values: @IntSource, @LongSource, @DoubleSource, @FloatSource

  • Date/time ranges: @InstantRangeSource, @LocalDateRangeSource, @LocalDateTimeRangeSource, @LocalTimeRangeSource

  • Date/time explicit values: @InstantSource, @LocalDateSource, @LocalDateTimeSource, @LocalTimeSource

  • Random date/time: @RandomInstantSource

  • Other types: @StringSource, enums, booleans

  • Values from a function, for data classes and nested objects: @ValuesFrom (see #values-from-a-function)

Date and Time Formats

Dates are read as yyyy-MM-dd, date-times as yyyy-MM-dd HH:mm and times as HH:mm, unless dateFormat, dateTimeFormat or timeFormat says otherwise. Instants are always ISO-8601.

Write MIN or MAX in place of a value for the type's own MIN or MAX. This works in every date and time value and range source, whatever the format:

@GeneratedParametersTest
fun acceptsEveryDate(@LocalDateSource(["MIN", "2024-02-29", "MAX"]) date: LocalDate) {
    // LocalDate.MIN, an ordinary date, LocalDate.MAX
}

@GeneratedParametersTest
fun lastWeekOfTime(@LocalDateRangeSource(min = "+999999999-12-25", max = "MAX") date: LocalDate) {
    // the last seven days LocalDate can hold
}
Content copied to clipboard

  • MAX is the type's exact maximum, such as LocalDateTime.MAX at 23:59:59.999999999, which HH:mm can't write.

  • Only the uppercase words are keywords; min and Max are parsed like any other value.

  • A range can run all the way to MAX and stops at the last value instead of overflowing. Mind the step, though: min = "MIN", max = "MAX" a day at a time is about 730 billion dates.

  • Dates near the edges can be written out too. The default formats accept the year 0 and negative years, as in -0500-03-15. A year always has at least four digits, and one with more than four needs its sign, as in +10000-01-01.

  • A custom format is used exactly as given. In a pattern, yyyy is the year of the era and can't be negative, so write uuuu to reach negative years with your own format.

  • The annotation processor accepts the same values at compile time.

  • @RandomInstantSource doesn't take the keywords, because it picks values by epoch millisecond, which can't reach Instant.MIN or Instant.MAX.

}

CI warning: two larger ranges can multiply quickly (for example, 100 x 100 = 10,000 invocations).

A product above one million invocations is refused before any test runs, with a message naming each parameter and its option count. Raise or lower that with a configuration parameter:

com.wesleyhome.test.jupiter.max.permutations=5000000

Pairwise Combinations

strategy = PAIRWISE runs enough combinations that every pair of parameters appears with every pair of their values, and no more:

@GeneratedParametersTest(strategy = PAIRWISE)
fun settings(
    @StringSource(["chrome", "firefox", "safari"]) browser: String,
    @StringSource(["windows", "mac", "linux"]) os: String,
    @StringSource(["en", "fr"]) locale: String
) {
    // 9 invocations instead of 18
}
Content copied to clipboard

Most defects are triggered by one value, or by two interacting. Pairwise keeps that reach for a fraction of the invocations, and unlike sampling it is a stated guarantee rather than a hope. What it gives up is combinations needing three or more specific values at once: in the example above chrome + windows + fr never runs.

Whether that trade is acceptable depends on what a test asserts, so it is opt in per method and never a default.

The saving comes from parameter count, not value count

Parameters Cartesian Pairwise
2 params, 3 values each 9 9, no saving at all
3 params (3, 3, 2) 18 9
6 params (3, 3, 2, 3, 3, 4) 648 ~12-16
10 params, 3 values each 59,049 ~15-20

With two parameters the single pair is the whole product, so there is nothing to collapse. Pairwise is a tool for wide test methods; it does nothing for @IntRangeSource(1..100) twice, which still yields 10,000 rows.

With filters

Say Safari only exists on mac:

@GeneratedParametersTest(strategy = PAIRWISE)
fun rendersOnSupportedPlatforms(
    @StringSource(["chrome", "firefox", "safari"]) browser: String,
    @StringSource(["windows", "mac", "linux"]) os: String,
    @StringSource(["en", "fr"]) locale: String
) { ... }

companion object {
    @JvmStatic
    fun rendersOnSupportedPlatforms_filter(browser: String, os: String): Boolean =
        browser != "safari" || os == "mac"
}
Content copied to clipboard

The pairs to cover are taken from the combinations the filter accepts, not from the value lists:

  • safari + windows is not a pair any accepted combination contains, so it is never demanded and never reported as missing.

  • safari + mac is reachable, so it is still guaranteed to appear.

Building a covering array first and filtering afterwards would instead drop whichever row happened to carry safari + mac, and the guarantee would quietly stop holding while still being advertised. That is the reason the two features are wired together rather than layered.

A compiled version of this, checked by the annotation processor, is examples.Pairwise in the examples module.

Notes

  • Selection is deterministic. The same test picks the same combinations on every run and every machine, and they are emitted in generation order.

  • Selection is greedy, so the row count is small but not provably minimal.

  • Pairwise reduces what runs, not what is generated, so the invocation ceiling still applies to the full product and generated.invocations still reports it. The report summary names the strategy when it is not CARTESIAN.

Filtering Combinations

A Cartesian product generates combinations that are invalid, not merely uninteresting - a start after its end, a currency that does not exist in the selected country. Skipping those in the test body with Assumptions.assumeTrue still generates, schedules and runs them, and reports them as skipped. A filter removes them before an invocation exists.

Name a method after the test and it applies automatically:

@GeneratedParametersTest
fun ordered(
    @IntRangeSource(min = 1, max = 3) start: Int,
    @IntRangeSource(min = 1, max = 3) end: Int
) {
    // runs 6 times, not 9
}

companion object {
    @JvmStatic
    fun ordered_filter(start: Int, end: Int): Boolean = start <= end
}
Content copied to clipboard

A filter declares only the parameters it is about, matched by name, so several small rules compose instead of one predicate that has to know about everything. A combination runs only if every filter accepts it. Use a suffix when a test has more than one:

@JvmStatic fun prices_filter_ordered(start: Int, end: Int): Boolean = start <= end
@JvmStatic fun prices_filter_currency(currency: Currency, country: Country): Boolean =
    currency in country.currencies
Content copied to clipboard

Name filters explicitly to share a rule between tests. Explicit and conventional filters both apply:

@GeneratedParametersTest(filters = ["startBeforeEnd"])
fun prices(...)
Content copied to clipboard

Rules

  • A filter must be static, or declared in a companion object. Filtering happens before the test instance exists, which is the same constraint @MethodSource has. Filters may live in a superclass.

  • Parameter types must match the generated parameter. A supertype is fine - Number accepts a generated Int - but a filter declaring Long against a generated Int is rejected rather than silently widened by reflection.

  • A filter must return Boolean and must not return null.

  • If every combination is rejected, the test fails and the message names the filters responsible.

  • Filtering reduces what runs, not what is generated, so the invocation ceiling still applies to the full product and generated.invocations still reports it.

The annotation processor warns about any *_filter method that matches no test in its class, so renaming a test cannot silently leave its rule unused.

Null Values

Add @WithNull to generate a null case alongside a parameter's other values:

@GeneratedParametersTest
fun handlesMissingName(@StringSource(["ada", "grace"]) @WithNull name: String?) {
    // runs with "ada", "grace", null
}
Content copied to clipboard
@GeneratedParametersTest
void handlesMissingName(@StringSource(values = {"ada", "grace"}) @WithNull String name) {
}
Content copied to clipboard

The null is generated last, after the parameter's other values.

A Kotlin parameter declared nullable also gets a null case today, inferred from its type. That inference is Kotlin-only - a Java Integer is nullable and never receives one - and it says nothing at the use site about what the test will run. It still works, but the annotation processor warns where it is relied on, and it will be removed in a future release. Prefer @WithNull.

@WithNull on a type that cannot hold null, such as a Kotlin Int or a Java int, is an error.

Value Classes

A parameter typed as a Kotlin @JvmInline value class takes its values from any source for the type it wraps. Each value is built through the class's constructor, so its init checks run:

@JvmInline
value class Money(val cents: Long) {
    init {
        require(cents >= 0) { "cents must be >= 0" }
    }
}

@GeneratedParametersTest
fun formatsAmounts(@LongSource([0, 1, 250]) amount: Money, @IntSource([1, 2]) quantity: Int) {
    // runs with Money(cents=0), Money(cents=1) and Money(cents=250), each with quantity 1 and 2
}

This works for value classes over primitives, String and object types. A custom provider can also produce the value class directly, for a type no built-in source covers:

@JvmInline
value class HouseholdId(val value: UUID)

@Target(AnnotationTarget.VALUE_PARAMETER)
@Retention(AnnotationRetention.RUNTIME)
@SourceProvider(HouseholdIdSourceDataProvider::class)
annotation class HouseholdIdSource

class HouseholdIdSourceDataProvider : AbstractAnnotatedParameterDataProvider<HouseholdId, HouseholdIdSource>() {
    override fun createParameterOptionsData(testParameter: TestParameter): List<HouseholdId> =
        listOf(HouseholdId(UUID.fromString("00000000-0000-0000-0000-000000000001")))
}

@GeneratedParametersTest
fun loadsHousehold(@HouseholdIdSource id: HouseholdId) {
}

If init rejects a generated value, the invocation that would have received it fails, and the others still run. The failure names the parameter, the value and the reason:

Generated value [-1] for parameter [amount] was rejected by Money: IllegalArgumentException: cents must be >= 0
Content copied to clipboard

A filter can't skip a rejected value either; the invocation runs and fails.

Display names and report entries show the value class's toString, such as Money(cents=250). @WithNull works on a nullable value class (amount: Money?). On a non-null value class over a primitive it is an error, because the compiled method takes a long there.

Filters can declare the value-class parameter as itself (fun formatsAmounts_filter(amount: Money)). Declaring the underlying type (amount: Long) is an error: both compile to long, so the Kotlin declaration is the only thing that tells them apart.

A value class with no source annotation is left to other parameter resolvers, even when it wraps a type such as Boolean that would otherwise be generated.

A compiled version of these, checked by the annotation processor, is examples.ValueClasses in the examples module.

Values From a Function

No annotation can spell out a data class or a nested object. @ValuesFrom takes a parameter's values from a function instead, and combines them with the other parameters like any other source:

data class DateRange(val start: LocalDate, val endInclusive: LocalDate) {
    fun overlaps(other: DateRange): Boolean = start <= other.endInclusive && other.start <= endInclusive
}

class DateRangeTest {

    @GeneratedParametersTest
    fun overlapsIsSymmetric(@ValuesFrom("ranges") a: DateRange, @ValuesFrom("ranges") b: DateRange) {
        // runs with every ordered pair of the three ranges: nine invocations
        assertEquals(a.overlaps(b), b.overlaps(a))
    }

    companion object {
        @JvmStatic
        fun ranges(): List<DateRange> = listOf(
            DateRange(LocalDate.of(2024, 1, 1), LocalDate.of(2024, 1, 31)),
            DateRange(LocalDate.of(2024, 1, 15), LocalDate.of(2024, 2, 15)),
            DateRange(LocalDate.of(2024, 3, 1), LocalDate.of(2024, 3, 31))
        )
    }
}
Content copied to clipboard

The function takes no arguments and returns a List, Sequence or array of the parameter's type. It is found by name the way a filter is: static, or in an object or companion object, on the test class or one of its superclasses. @JvmStatic is optional. To share a function between test classes, name its class as well:

object Fixtures {
    fun ranges(): List<DateRange> = listOf(/* ... */)
}

@GeneratedParametersTest
fun overlapsItself(@ValuesFrom("com.example.Fixtures#ranges") range: DateRange) {
    assertTrue(range.overlaps(range))
}

A top-level function is named by the class it compiles into: com.example.FixturesKt#ranges for one declared in Fixtures.kt.

@GeneratedParametersTest
void overlapsIsSymmetric(@ValuesFrom("ranges") DateRange a, @ValuesFrom("ranges") DateRange b) {
}

static List<DateRange> ranges() {
    return List.of(/* ... */);
}
Content copied to clipboard

Values from a function work with everything else:

  • Filters and pairwise: they see these values as they see any other.

  • @WithNull: adds a null case after the function's values.

  • Value classes: a function returning List<Money> works for a Money parameter.

  • Invocation ceiling: the function's values count toward it. Reading stops once the ceiling is passed, so an endless Sequence fails with a message instead of hanging the run.

The element type has to match the parameter's: List<Long> is not accepted for a Money parameter. A function whose elements may be null needs a nullable parameter or @WithNull. The annotation processor checks the name, the arguments and the return type at compile time. The same checks run when the test does, and each failure names the parameter and the function:

@ValuesFrom("ranges") on [a]: [ranges] returns String values, but [a] is DateRange

Generated vs Random Values

  • Range and explicit-value sources are deterministic by definition.

  • @RandomInstantSource draws from a fixed seed, so the same bounds produce the same sequence.

  • Invocation display names include resolved argument values, so failures show the generated value directly.

Change the seed to explore different values, deliberately rather than by accident:

@GeneratedParametersTest
fun expiry(@RandomInstantSource(min = "2024-01-01T00:00:00Z", max = "2025-01-01T00:00:00Z", size = 10, seed = 99L) at: Instant)

Offset bounds need a fixed clock

A fixed seed only makes a sequence reproducible if the range it draws from is also fixed. With useOffset = true the bounds are resolved against the current instant, so by default they move with the wall clock and a rerun tomorrow draws from a different window.

Fix the clock to make those reproducible:

# junit-platform.properties
com.wesleyhome.test.jupiter.clock.fixed.at=2024-01-01T00:00:00Z
com.wesleyhome.test.jupiter.clock.zone=UTC

or set one for a class or a run from an extension:

GeneratedParametersClock.set(extensionContext, Clock.fixed(instant, ZoneOffset.UTC))

Absolute bounds never depended on the clock and are unaffected by either.

Performance and Memory

Generation model:

  • Parameter value lists are generated eagerly per parameter.

  • Test invocations are iterated lazily across the Cartesian product.

Practical guidance:

  • Keep ranges intentional.

  • Prefer smaller random size values.

  • Split high-cardinality tests into targeted suites.

Concern @MethodSource Generated Sources
Boilerplate Requires separate provider methods Inlined annotation configuration
Type safety Depends on method return wiring Annotation-driven parameter typing
Range/date convenience Manual list/stream construction Built-in numeric and date/time sources
Compile-time validation Limited by default Supported via optional annotation processor

When a type needs a function, @ValuesFrom supplies one parameter's values rather than whole rows of arguments. The library still combines them, so a function listing three ranges gives every pair of ranges without writing the pairs out.

Custom Annotations and Providers

Define a parameter annotation, point it at a provider with @SourceProvider, and implement the provider. AbstractAnnotatedParameterDataProvider<T, A> recovers both the parameter type T and the annotation type A from the type arguments you supply, so it decides on its own which parameters to claim:

@Target(AnnotationTarget.VALUE_PARAMETER)
@Retention(AnnotationRetention.RUNTIME)
@SourceProvider(CustomSourceDataProvider::class)
annotation class CustomSource(val min: Int, val max: Int, val increment: Int)

class CustomSourceDataProvider : AbstractAnnotatedParameterDataProvider<Int, CustomSource>() {
    override fun createParameterOptionsData(testParameter: TestParameter): List<Int> {
        val annotation = findAnnotation(testParameter)!!
        return (annotation.min..annotation.max step annotation.increment).toList()
    }
}
Content copied to clipboard

Intermediate classes of your own between the provider and the library base are supported, so shared behaviour across several providers can live in a base class you control.

For a provider that claims a parameter by type alone, without an annotation, extend AbstractParameterDataProvider<T> instead and override only createParameterOptionsData.

To decide for yourself which parameters to claim, implement ParameterDataProvider<T> directly and supply both members:

class CustomSourceDataProvider : ParameterDataProvider<Int> {
    override fun providesDataFor(testParameter: TestParameter): Boolean =
        testParameter.annotations.any { it is CustomSource }

    override fun createParameterOptionsData(testParameter: TestParameter): List<Int> {
        val annotation = testParameter.annotations.filterIsInstance<CustomSource>().first()
        return (annotation.min..annotation.max step annotation.increment).toList()
    }
}
